讲解

第一步：Gemini Robotics 是什么——一个工长加一个熟练工（2026-11-20）

类比：装修队。 工长（看图纸、跟业主沟通、排工序、验收每一步）不亲手拧螺丝；熟练工（听一句"把这面墙刷了"就能干）不管整个工程的顺序。Gemini Robotics 就是这样一支队伍：

角色 模型 它是什么 输入 → 输出
工长（大脑） Gemini Robotics-ER（ER = Embodied Reasoning，具身推理） 一个 VLM，在 Gemini 上专门加强了"看懂物理世界"的能力 图像 / 视频 / 语音 / 文字 → 文字、指点坐标、检测框、计划、工具调用
熟练工（手） Gemini Robotics（VLA） 从 Gemini 微调出来、直接出动作的模型 图像 + 一句短指令 + 机器人自身状态（proprioception，本体感觉：关节角等）→ 一串动作
小号熟练工 Gemini Robotics On-Device 在机器人本地跑的小 VLA，底座是 Gemma（Google 的开放小模型） 同上，但不联网

GR 2 的博客把这三个模型并列介绍（gr-2-blog.txt L24–L30），并说 ER 2 是"机器人的高层大脑"（L62）。

每个模型背后都站着当时最新的 Gemini：1.0 建在 Gemini 2.0 上（1.0 报告 L109–L110），ER 2 建在 Gemini 3.5 Flash 上（gr-er-2-card.txt L37）。所以 Gemini Robotics 的核心赌注是：通用多模态大模型里已经有大量物理常识，只需要再教它"怎么动"。

开放程度（截至 2026-11）：

模型 谁能用
ER（1.5 起） 任何开发者，通过 Gemini API / Google AI Studio（gr-2-blog.txt L42）
VLA、On-Device 只给合作伙伴和 Trusted Tester（受信测试者）（同上 L42；gr-on-device-blog.txt L78）

一句话：Gemini Robotics 是一个"ER 当大脑 + VLA 当手"的模型家族，赌的是通用大模型的物理常识能迁移到机器人上；能公开调用的只有 ER。

第二步：两个模型之间传的是什么——一句话的子指令（2026-11-20）

类比：工长对工人说话，用的是人话，不是图纸坐标。 工长说"把左边那箱瓷砖搬到厨房"，工人自己决定怎么弯腰、怎么抓。

1.5 报告把这个系统叫做 agentic system（智能体系统），由两部分组成（L141–L152）：

部分 谁来当 做什么
Orchestrator（编排者） GR-ER 1.5 处理用户输入和环境反馈；把复杂任务拆成 VLA 能做的小步骤；做成功检测，决定什么时候进入下一步；需要时调用数字工具（搜索等）
Action model（动作模型） GR 1.5（VLA） 把编排者的指令翻译成底层动作；它对编排者来说就是一个工具，接收开放词汇的自然语言

ER 2 的博客说得更直白：开发者把 VLA、导航 API 等底层控制接口声明成工具，ER 2 去调用它们（gr-er-2-blog.txt L94）。这和你给大模型配一个"搜索"工具是同一种用法，只是这个工具会让机械臂动起来。

例子：1.5 报告举的"为去伦敦出差收拾行李箱"（L169–L178），一共拆了四层：

层 谁做 例子 时间尺度
用户任务 用户说 "Pack the suitcase for a trip to London" 整个任务
子指令 ER（查行程和天气后决定带什么） "把雨衣装进行李箱" 几十秒
短片段 VLA 的思考 "从衣柜里拿起雨衣" 几秒
原语动作 VLA 的思考（再细一层） "把夹爪往左移""合上夹爪" 不到一秒

ER 和 VLA 之间的接口是第二层：一句自然语言。好处是两个模型可以分开升级（ER 1.5 → 1.6 → 2，VLA 不用跟着改）；代价是一句话能表达的东西有限（精确位置、力度说不清），这个张力后面第 8 章会再回来。

GR 2 安全报告把这种分工叫"system 2 / system 1"架构（gr-2-safety-report.txt L38），并且指出编排者每次都在做一个路由决定（L63）：交给 VLA、问人、还是触发安全工具（急停）。第 13 章专门讲这个。

一句话：ER 把任务拆成一句句人话，把 VLA 当工具调用，并负责判断每一步做没做成。

第三步：慢大脑怎么跑出 50 Hz——动作块（action chunk）补延迟（2026-11-20）

类比：外卖。 厨房（云端大模型）出一单要 250 毫秒，你（机器人）每 20 毫秒就要吃一口。如果每单只送一口，你大部分时间在等；如果每单送 13 口，你吃完这一单时下一单刚好到。

1.0 报告 §3.1 给出了这笔账（L830–L837）：

  • VLA 拆成两半：云端 backbone（Gemini Robotics-ER 的蒸馏版，"distilled version"）+ 机器人本地的 action decoder（动作解码器）。
  • backbone 从"问到答"的延迟，从几秒优化到 160 ms 以内。
  • 加上本地 decoder，从原始观测到一块动作的端到端延迟约 250 ms。
  • 一块里有多个动作（引用了 ACT 的 action chunking），所以有效控制频率是 50 Hz。

公式：一次推理要覆盖的控制步数

\[K_{\min} = \lceil L \times f \rceil\]
  • \(L\)（读作"L"，latency 延迟）：从拍照到一块动作送达的时间，单位秒。
  • \(f\)（frequency 频率）：机器人执行动作的频率，单位 Hz（每秒几次）。
  • \(K\)（chunk 长度）：一块里有几个动作。\(\lceil\ \rceil\) 读作"向上取整"。
  • 如果 \(K < L \times f\)，每个周期都会有一段"动作用完、新块没到"的空档，稳态有效频率变成 \(K / L\)。

例子（\(f = 50\) Hz，即每步 20 ms）：

延迟 \(L\) \(L \times f\) \(K_{\min}\) 说明
100 ms 5 5 本地小模型量级
160 ms 8 8 只算 backbone（1.0 报告的上限）
250 ms 12.5 13 端到端（1.0 报告）

再看 \(L = 250\) ms 时 chunk 不够长会怎样：

chunk \(K\) 一块能覆盖 每个 250 ms 周期 稳态有效频率
13 260 ms 不卡 50 Hz
10 200 ms 卡 50 ms \(10 / 0.25 = 40\) Hz

注意：论文没有公开 chunk 长度，上面的 13 是按论文给的 250 ms 和 50 Hz 反推出来的"最低要求"。实际系统一般会让 chunk 比最低要求长一些、并在块与块之间做平滑；本地 decoder 也不只是"排队播放"，报告说它负责"补偿 backbone 的延迟"（L834），具体怎么补没写，第 4 章再细看。

一句话：大模型慢，就一次多给几步动作；延迟 × 频率 = 一块至少要覆盖的步数。

三条线各自的走向：

  • 能力：先让 VLA "会动"（1.0）→ 让它"先想再动"（1.5）→ 让 ER "看着视频盯进度"（2）→ 用前沿模型当研发引擎、扩大任务面（2.5 + Argon）。
  • 本体：一个双臂平台 → 三种身体一个模型 → 人形全身 + 灵巧手 + 多机 → 工厂产线。
  • 安全：语义安全问答 → 编排层的路由（拒绝 / 问人 / 急停）→ 对抗越狱和推理时引导。

一句话：八次发布按"能力、本体、安全"三条线读；1.0、1.5 有论文，之后只有博客和模型卡。

第五步：读官方数字的三个问题（2026-11-20）

类比：看商品广告。 "比上一代快 30%"——跟哪一代比？30% 是多少的 30%？测了几次？

官方博客里的数字大多是柱状图，读的时候先问三个问题：

问题 为什么要问 例子
跟谁比 baseline（基线）往往是自家上一代，不是别家最强 GR 2.5 的"30%–100% higher"是跟 previous baselines 比（gr-2-5-blog.txt L40）
绝对还是相对 0% → 93% 不可能是"相对提升"（从 0 涨多少倍都没意义） 见下表
测了多少次 真机试验少，误差条很宽；20 次和 200 次的 60% 可信度差很多 GR 2 博客的柱子带误差条（gr-2-blog.txt L34–L40），GR 2.5 博客的图注没写次数

例子（数字来自 GR 2.5 博客图注，L48 等）：

任务 GR 2 → GR 2.5 绝对提升 相对提升
用夹子装糕点 5% → 100% +95 个百分点（pp） ×20
合上工具箱盖 0% → 93% +93 pp 没有意义（旧值是 0）

再一个换算：把"成功率"换成"失败率"往往更能看出差距。GR 2.5 博客说 Argon 的越狱抵抗率 99.5%，上一个基线 ER 2 是 82%（L80）：

\[\frac{1 - 0.82}{1 - 0.995} = \frac{0.18}{0.005} = 36\]

被越狱成功的比例从 18% 降到 0.5%，降到原来的 1/36。而"82% → 99.5%"字面上只差 17.5 个百分点，看起来没那么夸张。

一句话：看官方数字先问跟谁比、绝对还是相对、测了几次；接近 100% 的数字换成失败率再比。

数学原理

  • 向上取整：\(\lceil 12.5 \rceil = 13\)。步数只能是整数，宁多勿少，少一步就会卡。
  • 稳态频率：每个周期长 \(L\)，执行 \(\min(K, Lf)\) 个动作，所以有效频率 \(= \min(K/L,\ f)\)。
  • 绝对 vs 相对提升：绝对 \(= p_1 - p_0\)（单位百分点）；相对 \(= p_1 / p_0\)，\(p_0 = 0\) 时没有定义。
  • 失败率之比：比较两个接近 1 的成功率时，用 \((1-p_0)/(1-p_1)\) 放大差距。

公式清单

公式 意思
\(K_{\min} = \lceil L \times f \rceil\) 一块动作至少要覆盖的控制步数
\(f_{\text{eff}} = \min(K / L,\ f)\) chunk 不够长时的稳态有效频率
\(\Delta_{\text{abs}} = p_1 - p_0\)，\(\Delta_{\text{rel}} = p_1 / p_0\) 绝对提升（百分点）、相对提升（倍数）
\((1 - p_0) / (1 - p_1)\) 失败率降到原来的几分之一

关键几行：

dt = 1000 // hz                       # 50 Hz → 每步 20 ms
for t in range(0, total_ms, dt):
    while next_arrival <= t:          # 新动作块到了
        buffer, next_arrival = chunk, next_arrival + latency_ms  # 替换旧块，下一次请求马上发出
    if t < latency_ms: continue       # 开机等第一个块，不算卡顿
    if buffer > 0: buffer -= 1        # 执行一个动作
    else: stalled += 1                # 没动作可执行：卡顿

代码里才看得到的 3 件事：

  1. 模拟按 20 ms 的整数格走，250 ms 的到达时刻落在两格之间，所以"卡顿 540 ms"不是精确的 \(11 \times 50\) ms，而是格子取整后的结果；稳态频率仍然是 40 Hz。
  2. chunk=13 时模拟出 49.8 Hz 而不是 50 Hz：统计区间从第一个块到达（250 ms）开始，第一格落在 260 ms，少算了一步。
  3. 新块替换旧块（剩下的旧动作丢掉），这是最简单的做法；真实系统常在新旧块之间做平滑（如 ACT 的 temporal ensembling），第 4 章再讲。

自己改一改（不影响练习答案）：

  • 把 CONTROL_HZ 改成 30，看 250 ms 延迟下 \(K_{\min}\) 变成多少。
  • 给 simulate_chunk_stream 加一个"新块不替换、而是接在旧块后面"的选项，比较两种做法的卡顿时长。
